This is a new minor release of the `alex-c-line` package. It introduces new features and other backwards-compatible changes that should require little to no refactoring. Please read the description of changes below.
<!-- alex-c-line-release-summary-end -->

## Description of Changes

<!-- user-editable-section-start -->
- Add a migrations mechanism for the global config
  - We need to manage the global config in such a way that updating `alex-c-line` won't break global config parsing due to the config potentially being outdated, while still allowing for downgrades so that newer config versions don't break older ones either.
  - As such, the system I have in mind is to have each configuration file is numbered, and each version of `alex-c-line` tracks the exact migration number it is currently on. It will then always reference the config file with that migration number for as long as you're on that version of `alex-c-line`.
  - To migrate to newer versions seamlessly a migrations system is in place where files in `src/configs/migrations` are named numerically, and the intent is that each migration file defines how you get to the current file from the previous.
  - This will always run on start-up and it will skip running migrations for files that already exist.

## Additional Notes

- Given that this contains a migration of the global config file (since this sets them up to begin with), this is a minor release because even though it ideally shouldn't affect users it does change the way the global config is managed, which does have the potential to break existing usage.
- Migrations in general are considered medium risk as a bad migration could potentially lead to data loss, and so they should always be handled with care.
- For global config, the data is at least not super sensitive and is relatively easy to reconstruct if lost, but it definitely still would be very annoying to lose all your configuration settings so we still treat it with the same respect as we do with, for example, database migrations in Lexicon.
